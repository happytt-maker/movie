# 答辩记录与问题准备

## 一、可能被问到的问题与回答要点

**Q1：为什么不用评分预测（RMSE）而用排序指标？**
任务书的核心指标是 NDCG@10，衡量的是"正样本有没有排进前 10"，与评分误差不是一回事。
我们做过对照：同样用矩阵分解，评分回归 + 热门补全的 NDCG 只有 0.736 量级，换成 BPR 成对
目标后是 0.856。训练目标必须和评价指标对齐，这是本项目最重要的一条经验。

**Q2：怎么保证没有数据泄漏？**
三层约束：① 按每个用户的时间戳切 8:1:1，训练集只用前 80%；② 候选集的负样本从"用户没有
交互过的条目"里采样，采样池只用训练期统计；③ 验证集只用于早停和选参，测试集只在最终评估
时用一次。旧模型是在随机划分上训练的，直接拿来用会有泄漏，所以我们只继承它的 embedding，
在时间划分上重新训练。

**Q3：旧模型到底带来了多少收益？怎么证明？**
做了对照实验：同样 4 轮 BPR，随机初始化 NDCG@10 = 0.8028，用旧评分 MF 的 embedding 热启动
= 0.8562，相对提升 6.6%。两个实验的划分、候选集、负采样、种子完全一致，只有初始化不同。

**Q4：为什么 NDCG 能到 0.89 这么高？**
候选集是 1 个正样本量级（平均 8.2 个正样本）对 100 个负样本，正样本占比约 7.6%，比全库
排序容易得多；且测试正样本本身就来自"用户会给高分"的分布。0.89 说明模型能稳定把正样本
排进前 10，但不代表全库检索也同样好——这一点在报告局限性里写明了。

**Q5：LSH 召回率为什么只有 0.148？**
MinHash 估计的是集合 Jaccard 相似度，这份数据的用户集合非常稀疏、相似度分布扁平，阈值 0.3
会把绝大多数"真正相似"的条目对也过滤掉，所以平均只召回 23.9 个候选。正确做法是按 Jaccard
分布自适应选阈值，或增加 bands、改用加权 MinHash。我们如实保留了负面结果并分析了原因。

**Q6：Spark 那部分到底做了什么，还是只是调包？**
做了三件事：① 把 12.9M 条正反馈导出成分布式可读格式并校验行数；② 用 MLlib ALS 隐式模式
训练（rank 64、alpha 10、10 轮），记录每阶段耗时（读取 11s、训练 564s、打分 28s）；③ 在
20k 抽样用户上评估 NDCG 0.79，并写了 `--scales` 支持 25%/50%/100% 数据规模的扩展性实验。
过程中还解决了 Windows 下中文路径导致 JVM 报 `Bad pathname`、以及 Python 侧建 SparkSession
挂起必须走 spark-submit 两个环境问题。

**Q7：流式处理的状态是怎么设计的？**
每个事件到达时更新三类状态：采样（Bernoulli + 蓄水池）、24 小时滚动窗口（事件量、均分、
类型分布）、用户类型画像（计数，支持按天衰减）。关键是增量更新而不是全量重算：单次画像更新
1.73 微秒，3.29M 事件 41.7 秒跑完，吞吐 78,939 事件/秒。最后用批量计算校验了画像计数与
流式结果完全一致。

**Q8：图那部分为什么 PageRank 没用，社区特征却有用？**
二部图上的 PageRank 主要由节点度数决定，所以它排出来的顺序几乎就是热门顺序（0.7451 vs
0.7453），单独用没有意义。但 Louvain 划出的社区捕捉的是"用户群和电影群的结构性对应关系"，
把"用户历史在哪个社区、该电影是否属于这个社区"做成特征后，NDCG 从 0.7453 提到 0.7791，
说明图信号要以社区/子结构的形式进入模型才有价值。

**Q9：消融实验说明了什么？**
去掉 BPR 分数后 NDCG 从 0.8894 掉到 0.8417（−5.4%），说明召回分是主力；去掉类型亲和度掉到
0.8727（−1.9%），说明类型特征提供了 BPR 内积表达不了的上下文信息。其余特征贡献较小，
可以精简。

**Q10：如果给你更多时间，优先改什么？**
① 把 LSH 参数调好，或换成 HNSW 做近似召回；② 社区特征接回全量排序（现在是 20k 用户子图）；
③ 流式部分换成 Structured Streaming 的 `mapGroupsWithState`；④ 加序列特征和双塔召回。
