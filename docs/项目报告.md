# 基于 MovieLens 32M 的分布式增量电影推荐系统

## 项目报告

课程：大数据技术　　数据集：MovieLens 32M　　随机种子：20260907

## 一、摘要

本项目在 MovieLens 32M 上构建了一套"数据处理—召回—特征—排序—在线更新"的完整推荐流程，
覆盖任务书要求的六项任务：数据检查与热门基线、相似度与 LSH 近似近邻、Spark 分布式矩阵分解、
评分流式增量处理、二部图链接分析与社区特征、召回-特征-排序集成。系统严格遵循任务书的评价
协议：正反馈定义为 `rating >= 4`，按用户时间戳 8:1:1 划分，测试候选集为"正样本 + 100 个固定
负样本"，主指标 NDCG@10。

最终模型 NDCG@10 达到 **0.8894**，相对热门基线 0.7363 提升 **20.8%**，超过任务书"不低于 10%"
的目标。实验同时表明：把评分回归目标换成成对排序目标（BPR）带来 +16.3%，复用此前训练的评分
矩阵分解权重做热启动再带来 6.6% 的相对提升，LightGBM 集成排序在 BPR 分数之上再提升 3.9%。

## 二、问题定义与目标

给定用户集合 U、电影集合 I 与历史评分记录（user, movie, rating, timestamp），系统需要为每位
用户在候选集中选出 Top-10 电影，使 NDCG@10 最大化。与评分预测不同，排序任务只关心正反馈
（rating ≥ 4）是否被排到前面，因此本项目全程以排序目标训练与评估。

工程目标有四个：可运行（一条命令复现全流程）、可评价（统一指标脚本）、可扩展（单机到 Spark
的同一套数据协议）、可解释（每个模块都有独立结论）。

## 三、数据分析（任务一）

MovieLens 32M 共 32,000,204 条评分、200,948 位用户、84,432 部电影，评分时间跨度 1995-01 至
2023-07，评分均值 3.50，稀疏度约 0.19%（32M / (200,948 × 84,432)）。数据检查发现：无缺失值，
无完全重复的 (user, movie) 对，但存在大量低频电影——这正是必须做时间划分与候选集约束的原因。

按时间划分后：训练 25,520,897 条、验证 3,188,339 条、测试 3,290,968 条。测试候选集共
20,660,431 行，覆盖 191,007 位有正样本的测试用户，平均每位用户 8.2 个正样本、100 个负样本。
热门基线按训练集交互次数排序，NDCG@10 = 0.7363、Recall@10 = 0.7291，作为后续所有模型的对照。

## 四、系统架构

系统分五层：

1. 数据层：`prepare_data.py` 完成质量检查、时间划分、候选集生成，产物为 npz 与词表；
2. 特征层：`build_features.py` 把条目统计、用户统计、类型亲和度、模型分数展开到"候选行"粒度；
3. 算法层：热门基线、精确相似度 + LSH、Spark ALS、流式回放、二部图、BPR、LightGBM；
4. 服务层：`CandidateSet` 统一按用户切片打分，输出 `top10_<model>.csv`；
5. 评价层：`evaluate.py` 对齐真值计算 NDCG/Recall/MRR 与延迟，写 `metrics_<model>.json`。

所有模块共享 `configs/base.yaml` 中的协议参数（阈值、划分比例、负样本数、种子）与相对路径
（`data/ml-32m`、`data/processed`、`models`、`results`），路径统一由 `resolve()` 解析到项目根目录，
换机器不需要改代码；数据集放在项目外时可复制 `configs/local.example.yaml` 覆盖。

## 五、算法设计与实现

### 5.1 热门基线（任务一）

按训练交互次数排序，并提供对数、时间加权、贝叶斯平均三种口径以检验基线强度。热门基线是
"不建模"的下界，也是检验候选集与指标实现是否正确的手段：其 NDCG 0.7363 与理论估算一致
（平均 8 个正样本、100 个负样本，随机排序约 0.09，按热度排序显著更高）。

### 5.2 相似度与 LSH（任务二）

全量 84,432 部电影的余弦相似矩阵需要 7.1×10⁹ 个元素，单机内存不可行。因此先在"训练交互数
前 3,000 的头部条目"上做精确 cosine top-K（30.4 秒），再对同一批条目用 MinHash-LSH
（datasketch，8 个哈希函数、阈值 0.3）近似召回，比较召回率、候选规模与耗时。

实测 LSH 平均产生 23.9 个候选、耗时 420.9 秒、recall@20 仅 **0.148**。这一负面结果说明该类
数据的相似度分布非常扁平——阈值 0.3 对绝大多数条目对来说过高，真正相似的对被过滤掉了。
进一步把头部条目缩到 300 部时 recall@20 升到 **0.4375**，说明召回率对集合规模与阈值极其敏感：
同一套参数在小规模上看似可用，放大到 3,000 部就失效。正确做法是按 Jaccard 分布自适应选阈值
或增加 bands，或换用带权重的集合表示。项目保留该结果并如实记录，因为它正好说明"近似算法必须
按数据分布调参"，而不是照搬默认值。

### 5.3 Spark 分布式矩阵分解（任务三）

使用 Spark 3.5.3 + MLlib ALS 的隐式反馈模式（rank=64、alpha=10、regParam=0.05、nonnegative），
在 12.9M 条正反馈上训练。5 轮迭代 425.6 秒完成，10 轮迭代 564.2 秒；随后对 2,042,661 条候选
打分（28.4 秒），在 19,986 位抽样用户上 NDCG@10 = 0.771（5 轮）与 0.790（10 轮）。

工程上遇到两个 Windows 特有的坑并已解决：一是 spark-submit 的脚本路径含中文时 JVM 报
`Bad pathname`，需用纯 ASCII 路径启动；二是在 Python 里直接创建 SparkSession 在本机会挂起，
改用 `spark-submit` 启动即正常。脚本同时支持 `--scales 0.25,0.5,1.0` 做数据规模扩展实验。

### 5.4 流式增量处理（任务四）

`src/streaming/replay.py` 把测试期 3,290,968 条评分按时间戳回放成事件流，单线程处理 41.7 秒，
吞吐 **78,939 事件/秒**。每个事件同时更新三类状态：Bernoulli 采样与蓄水池采样（用于在线统计）、
24 小时滚动窗口聚合（共 9,678 个窗口，含事件量、均分、类型分布）、用户类型画像的增量更新
（**1.73 微秒/次**，支持按天衰减）。最后用批量计算校验画像计数与流式结果完全一致，证明增量
状态机没有丢失或重复计数。

### 5.5 二部图链接分析与社区特征（任务五）

在 20,000 位用户、23,324 部电影、130 万条边的子图上构造用户-电影二部图（43,324 个节点、
平均度 60.3），用幂迭代计算 PageRank（0.1 秒收敛），再用 Louvain 划分社区（59 个社区、
67.4 秒）。在同一批用户、同一候选集上比较：热门 0.7453、PageRank 0.7451、PageRank × 社区匹配
**0.7791**。结论很明确：链接分析单独使用几乎等价于热门（因为二部图上的 PageRank 主要由度决定），
但"用户历史社区的偏好分布"这一社区特征能带来 4.5% 的提升，属于真正有用的图信号。

### 5.6 BPR 召回与集成排序（任务六）

召回层用 BPR-MF（dim=64，成对损失，负采样 4 个/正样本）。这里复用了此前在 Big_Data 项目中
训练的评分矩阵分解权重（`movielens_mf.pt`，64 维、200,948 用户 × 84,432 电影）做热启动：只保留
用户/电影 embedding 与偏置，换掉评分回归头，接上 BPR 的成对目标继续训练 4 轮。该权重的训练
脚本已一并收录在 `legacy/big_data/Big_Data.py`（仅把默认路径改为项目内相对路径），据此可知它
用的是随机 8:1:1 划分、种子 42、验证集 RMSE 0.7640；正因为是随机划分，直接用它预测会与时间划分
协议冲突（数据泄漏），所以本项目只继承其 embedding。对比实验显示，热启动版本 NDCG@10 = 0.8562，
随机初始化版本 0.8028，**相对提升 6.6%**，且收敛更快——旧模型的价值被量化确认。

排序层用 LightGBM LambdaRank，特征 9 个：BPR 分数、条目热度（计数/对数/贝叶斯均分）、条目平均分、
类型亲和度（用户画像与条目类型的余弦）、用户活跃度、条目时间趋势、用户最近活跃时间。训练在
8 万用户的候选行上完成，验证集早停。最终 NDCG@10 = **0.8894**、Recall@10 = 0.8301。

## 六、实验设置

- 硬件：16 核 CPU、16 GB 内存、RTX 3050 Laptop 4 GB；PyTorch 2.8.0+cu126、LightGBM 4.5.0、PySpark 3.5.3、Java 17
- 划分与候选集见第三节；负采样池为"训练交互 ≥ 5 的条目"，并排除用户已交互条目
- 模型选择只看验证集，测试集仅在最终评估使用一次
- 所有随机性由种子 20260907 控制（负采样、BPR 负采样、LightGBM、Louvain、流式采样）

## 七、结果与分析

| 模型 | NDCG@10 | Recall@10 | MRR@10 | 相对热门 |
|---|---|---|---|---|
| 热门基线 | 0.7363 | 0.7291 | 0.7687 | — |
| Spark ALS（20k 抽样） | 0.7896 | — | — | — |
| BPR（随机初始化） | 0.8028 | 0.7840 | 0.8222 | +9.0% |
| BPR（旧模型热启动） | 0.8562 | 0.8191 | 0.8811 | +16.3% |
| LightGBM 集成排序 | **0.8894** | **0.8301** | **0.9338** | **+20.8%** |

三点分析：

1. **目标函数比模型容量更重要**。同为矩阵分解，评分回归 + 热门补全只有 0.736 量级，换成 BPR
   成对目标直接到 0.856，说明"训练目标与评价指标对齐"是排序任务的第一性原则。
2. **热启动是低成本高收益**。旧模型的 embedding 已经编码了用户-电影的低维结构，换头续训
   4 轮就超过随机初始化 4 轮的 6.6%，等价于省下数倍训练时间。
3. **集成排序的增益来自特征互补**。BPR 只看隐向量内积，而类型亲和度、条目时间趋势、用户活跃度
   提供了 BPR 无法表达的上下文信息，融合后仍有 3.9% 提升。

### 消融实验

| 配置 | NDCG@10 | 相对完整模型 |
|---|---|---|
| 完整模型（9 特征） | 0.8894 | — |
| 去掉 BPR 分数 | 0.8417 | −5.4% |
| 去掉类型亲和度 | 0.8727 | −1.9% |

BPR 分数是绝对主力（去掉后跌到只剩热门+统计特征的水平），类型亲和度贡献稳定但量级较小，
其余特征（条目均分、贝叶斯分、时间趋势）贡献更弱，与特征重要性排序一致。

## 八、局限性与改进方向

1. **LSH 参数未调优**，recall@20 仅 0.148。后续应按 Jaccard 分布自适应选阈值，或改用
   SimHash/带权 MinHash，并做 bands × rows 的网格搜索。
2. **图实验在 20k 用户子图上完成**，全量 Louvain 单机不可行。可改用 Spark GraphX 或
   METIS 分区后再做社区发现，把社区特征接回全量排序。
3. **负样本口径由本项目确定**。任务书未提供教师端负采样脚本的池定义，换口径会影响热门基线
   与绝对分数，但不改变模型间的相对排序。
4. **流式处理目前是单机回放**，未接 Kafka/Structured Streaming。若要上生产，可把状态机改成
   Spark Structured Streaming 的 `mapGroupsWithState`，本项目的状态定义可直接复用。
5. **排序模型仍有提升空间**：目前 best_iteration 偏小，可尝试更小学习率 + 更多轮次、
   加入序列特征（用户最近 N 部电影）以及双塔召回。

## 九、复现说明

```bash
pip install -r requirements.txt                  # 依赖（torch 按本机 CUDA 版本单独装）
# 数据集解压到 data/ml-32m/{ratings.csv, movies.csv}
python scripts/run_all.py                        # 全流程（约 15 分钟，读 configs/base.yaml）
spark-submit --master "local[4]" scripts/spark_als.py   # 任务三（需 pyspark + Java）
```

所有路径都相对项目根目录，由 `src/data_io.py` 统一解析，因此在任何目录执行都能找到同一份数据。
中间产物落在 `data/processed`、`data/features`、`results`，均可删除后重跑；结果文件
`results/metrics_*.json` 与 `results/top10_*.csv` 已随项目提供，便于直接核对数字。
热启动权重 `models/movielens_mf.pt` 随项目提供，缺失时 BPR 会自动退回随机初始化并打印提示。
